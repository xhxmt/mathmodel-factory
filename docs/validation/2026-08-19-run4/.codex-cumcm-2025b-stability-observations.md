## Step-12-to-Step-3 rewind postmortem

1. The event history contains two Stage-8/Step-12 revision reopens to Stage 3: revision 922 at `2026-08-17 21:53:54 Asia/Hong_Kong`, and revision 1151 at `2026-08-18 11:08:36 Asia/Hong_Kong`. The latter is the ownership-classifier incident discussed here.
2. Revision 1151 was not evidence that the reviewer had invalidated the whole mathematical approach. Step 12 added `models/m2_airy/08_block_length_extended.py` and `results/**/block_length_extended*.json`; the live worker had loaded the pre-fix registry and classified them as Stage-3/Stage-9 artifacts, even though a fresh process using the corrected registry classified both as Stage 8. It emitted `Stage 8 changed content owned by Stage 3` and `resume_after_step=3` under a mismatched classifier identity. This rewind trigger was a scheduler bug.
3. A classifier rebase can retire the false active dirty obligations, but the current semantic-reopen transaction has already invalidated every downstream checkpoint after Step 3. The state store is append-only and has no supported operation that re-attests and restores those invalidated checkpoints. Therefore fixing the classifier alone cannot safely return the cursor to Step 12; manually editing `project_state` would fabricate completion and break the evidence chain.
4. At the instant of the false rewind, the desired behavior was to reclassify the causes and revalidate the existing Step-4-through-Step-12 checkpoints without dispatching agents. The absence of that recovery primitive is the main reason an ownership bug expanded into a long recovery chain. This should not be described as intrinsically requiring a full rerun.
5. During the recovery chain, the artifact identity genuinely changed. A Step-4 agent updated `quality_contract.json`, `model.md`, `symbol_table.md`, auxiliary scaffolds, and model code to retain the reflection phase difference `Delta phi`; the quality contract is Stage-3-owned. Step-5 provenance then correctly rejected historical canonical outputs with `SUBMITTED_CODE_OR_INPUTS_CHANGED`, and canonical/derived artifacts had to be refreshed. After these real changes, directly forcing the cursor back to Step 12 was no longer valid even though the original rewind trigger had been false.
6. Recovery is intended to be validation-led rather than a blind full recomputation: unchanged stages may be promoted by their existing validators and prompt-input receipts; only stages whose code/input/output identity changed should dispatch agents or solvers. In this incident Stage 3 and Step 5 required real re-attestation, while later stages should reuse artifacts whenever current hashes and receipts pass.
7. The semantic-reopen budget had a related defect. Stage 4 had two historical reopen events, but one was caused only by `models/**/*.log` being routed to Stage 3 under an obsolete classifier. The old implementation counted all historical reopens forever, so the later legitimate `quality_contract.json` change failed with `PERMANENT_STAGE_SEMANTIC_REOPEN_EXHAUSTED`. The repair records `classifier_contract_sha256` on new reopen/failure events and counts the budget against the current classifier contract, using the latest explicit rebase as the migration boundary for legacy events. The scheduler/service/state-store regression set passed 108/108 tests.
8. After the audited repair, formal recovery moved the failed Step-5 state to `READY / last_completed_step=3` at revision 1479. A standard-tier Codex Step-4 run (`gpt-5.6-sol/xhigh`, `CODEX_SERVICE_TIER` unset) passed the model audit, 12/12 project tests, and the dual implementation checks, then committed `last_completed_step=4` and prepared Step 5 at revision 1485.

Required system repair: add an append-only `revalidate-invalidated-checkpoints` or `restore-checkpoints-after-classifier-rebase` lifecycle. It must (a) bind the current classifier and canonical code root, (b) prove the original reopen causes are retired or migrated, (c) replay each invalidated stage validator against current artifact and prompt-input fingerprints, (d) restore only byte-identical, validator-passing checkpoints without launching agents, and (e) emit a receipt listing every reused, regenerated, and still-invalid stage. The frontend must distinguish `false ownership rewind`, `checkpoint revalidation`, and `real upstream content change` instead of presenting all three as a generic return to an earlier step.
